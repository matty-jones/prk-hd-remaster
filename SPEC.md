# Project Rubi-Ka HD Remaster Factory

**Engineering specification / Cursor implementation brief**  
**Version:** 1.0 | **Date:** 31 October 2026 | **Status:** Ready to implement  
**Working name:** `prk-hd-remaster` (rename freely)

## 0. Directive to the implementation agent

Build a **working, local, automated, high-impact texture re-authoring production system** for Project Rubi-Ka (PRK) that emits a directly installable **ao-vk texture pack**. Build the system **and run the first complete 1,076-texture production cohort** on the user's RTX 5080 if the client database, catalogue, model weights and GPU are accessible in the execution environment. Do not stop at architecture documents, an inference toy, a mock gallery, an example texture, or a comparison between three upscalers.

**One selected path:** **Qwen-Image-2.1-Turbo (image-conditioned generative re-authoring) -> PBRFusion 4 (normals/depth) -> material-aware ORM and height processing -> automated QA -> ao-vk pack -> in-game evidence.** Keep the system modular enough to fix failures, but **do not** spend the initial project comparing Real-ESRGAN, SeedVR2 and other workflows. Only substitute a simpler re-authoring model if the chosen model proves untenable on this hardware after quantisation/offload attempts, and document the reason.

The actual purpose is a **visible transformation** of AO's rock, terrain, architecture, metal and interior surfaces, while retaining the layout, palette, location identity and recognisable details of the source game. Optimise for improved *in-game visual fidelity*, not PSNR against a 2001 JPEG.

Treat the user as technically capable, working on **Kubuntu/Linux with an RTX 5080 16 GB**, using **Cursor**, Python and existing PRK/ao-vk projects. Avoid redundant research and proof-of-concept work. Follow this spec, exercise judgement on unimportant implementation choices, and record genuine blockers accurately.

### 1.2 ao-vk already supports the required output

Existing project: <https://github.com/matty-jones/ao-vk> (known user fork; previously inspected main commit `ab587fd30ec3384b36a1d1dd7f99615e2ad46578`; verify the current checkout rather than assuming that SHA is still latest). Relevant upstream docs:

- <https://github.com/matty-jones/ao-vk/blob/main/docs/materials.md>
- <https://github.com/matty-jones/ao-vk/blob/main/docs/live-meshes-plan.md>
- <https://github.com/matty-jones/ao-vk/blob/main/docs/pipeline.md>

For texture ID `TYPE:ID`, the renderer accepts these **side-loaded PNGs** (RDB ID, not name, is the identity):

| File pattern | Meaning |
|---|---|
| `<type>_<id>_d.png` | Replacement albedo, including preserved alpha |
| `<type>_<id>_n.png` | Tangent-space normal map, **OpenGL +Y convention** |
| `<type>_<id>_h.png` | Height, greyscale; used for parallax and normal processing |
| `<type>_<id>_orm.png` | **R=occlusion, G=roughness, B=metallic**, glTF packing |
| `<type>_<id>_e.png` | Emissive map, only when warranted |

The renderer creates mipmaps at load. Material files for a given source texture should be in the **same winning pack**, because the pack selection resolves a texture's maps as a unit. Material packs go under `<PRK client>/randy-vk/packs/<pack-name>/`, selected by `<PRK client>/randy-vk/packs/order.txt` (review existing order and precedence). **Do not change `rdb.db`, replace `randy31.dll`, or edit PRK gameplay files.** A pack can be disabled by removing its entry from `order.txt`; an installer must preserve previous pack order and offer a clean rollback.

### 1.3 Model stack and verified constraints

**Primary generator:** [Qwen-Image-2.1-Turbo](https://huggingface.co/Qwen/Qwen-Image-2.1-Turbo), official 8-step text-to-image **and image-conditioned editing** checkpoint. Diffusers `QwenImage21Pipeline` accepts `prompt` and `image`; the checkpoint supplies its own sampling schedule. Do **not** assume Turbo supports base-model negative prompts, arbitrary CFG or a manually imposed sampler schedule. Native architecture contains a 7B visual generator, a Qwen3-VL-8B vision/text encoder and VAE. It is **not a 7B-only VRAM load**.

**Local execution:** adopt **ComfyUI with the official Qwen 2.1 Turbo image-edit workflow** as the default model worker, controlled via its local queue/API, with Python orchestration. Choose quantised diffusion/vision components, component offloading and low-VRAM mode appropriate to the RTX 5080 16 GB. The official model can alternatively be run through Diffusers, but this is an implementation alternative for reliability, not a parallel model comparison. The separate prompt-enhancement encoder is optional; omit it by default to conserve memory. Pin exact versions, custom nodes, model IDs and SHA-256/revisions in a model lockfile. Record actual allocated VRAM and wall time. **Do not promise that 2K generation fits 16 GB at full precision**: obtain a functioning quantised/offloaded route first. No paid API or cloud processing is part of the default system.

Official model / implementation references:

- <https://github.com/QwenLM/Qwen-Image-2.1>
- <https://huggingface.co/Qwen/Qwen-Image-2.1-Turbo>
- <https://huggingface.co/docs/diffusers/en/api/pipelines/qwenimage21>
- <https://github.com/Comfy-Org/docs/blob/main/tutorials/image/qwen/qwen-image-2-1.mdx>

**PBR generation:** [PBRFusion 4](https://huggingface.co/NightRaven109/PBRFusion4), [ComfyUI nodes](https://github.com/Night1099/COMFYUI-PBRFusion4). The published model provides **learned normal and depth**, with OpenGL normal output selectable, and 8 GB recommended minimum. It does **not** promise a complete learned albedo + ORM generator. Use its depth estimate as a *relative* relief input, not a metrically calibrated height field. Implement roughness/metallic/occlusion using material-aware rules and optional image analysis. Cite inputs and methods in the report. Do not silently label made-up roughness as physically validated.

6. Generate a **real visual review gallery** with original/generated comparisons and 3x3 tiled views. Include in-game screenshot instructions and a before/after evidence folder using the actual pack. Automated in-game screenshot capture is optional if fragile, but the pack must be usable in PRK.

**No additional 100-image model bake-off is required.** Small smoke calls are permitted only where technically needed to prove the model loads, a tensor has the correct shape, or an output file can be written. Immediately continue into real production after those checks.

## 5. Generation recipe: deliberately high-impact

### 5.1 Qwen as an image editor, not a text-only texture generator

Every source image is passed to Qwen **as conditioning image**, with a prompt assembled from:

- material class and family;
- artist filename and meaningful semantic tags;
- texture type: repeating surface, nonrepeating decorative surface, stone, metal, wall, etc.;
- aspect ratio, source size and target size;
- reference to other images in the same family **only when it improves consistency** and fits the memory budget;
- negative restrictions phrased **positively** because Turbo does not necessarily support negative prompts/CFG semantics of the base checkpoint.

**Default creative direction:** richly detailed, modern, believable PBR-ready surfaces with substantially more microstructure than the source, faithful recognisable colour/material identity, straight-on/orthographic surface appearance, no simulated directional lighting, no baked cast shadows, no photographic camera perspective, no lettering or added objects, no borders, no watermarks. Preserve large structural motifs, major seams and placements where the UV layout requires them.

Example material-specific prompts (templates, not immutable literals):

```text
TERRAIN_STONE:
Re-author the supplied original Anarchy Online ground/rock texture as a premium
modern-game albedo map. Keep the identifiable palette, arrangement, rock type
and silhouette/feature placement. Invent convincing mineral grain, weathering,
fractures, granular scale variation and fine surface detail. Orthographic,
unlit, uniform exposure. Seamless periodic tile where marked. Preserve the
source's recognisable visual identity while delivering a substantial visual
upgrade. Output one square albedo texture, no separate scene or typography.

PAINTED_METAL:
Re-author this source texture as modern high-resolution game material,
faithfully retaining the original panel pattern, colour blocks, boundaries and
important markings. Add convincing micro-scratches, paint texture, wear and
physically plausible surface detail. Straight-on, diffuse/albedo appearance,
without baked reflections or dramatic shadows. Maintain UV registration.
```

**Variation strategy:** same family shares a style prompt and material policy, each texture receives its own conditioned output; deterministic per-asset seed derived from `(model revision, job config, type, id, source SHA)`. A rerun with same seed is intended to be reproducible, but GPU kernels/quantisation may limit bit-identical results. Track input/model/version/seed alongside output SHA.

### 5.2 Resolution policy

Start with **substantial new generated detail**, not mere 4x pixel replication. Preserve each texture's **aspect ratio** and mapping. Default aim:

- Ordinary 128–256px source surfaces: **1024px or 2048px long side**, class-dependent. Make the choice configurable by texel density and likely onscreen coverage; favour 2K for prominent ground, walls and stone.
- 512px or larger important materials: 2K default; 4K only when visual coverage warrants it and the pipeline can genuinely generate useful detail.
- Tiny masks, decals, icons and UI: **no indiscriminate Qwen generation**.

Qwen native 2K editing is an **aspiration subject to 16 GB VRAM**. On OOM, first use supported quantised weights, sequential component offloading, smaller attention/latent settings and smaller internal generation size; an in-pipeline resolution-completion step may be used, provided the **generative re-authoring stage remains Qwen** and the output is clearly labelled. Do not quietly call a bilinear-upscaled 2K image a native 2K AI-generation success. Do not load Qwen and PBRFusion into VRAM simultaneously unless measured safe; use separate worker lifetimes or unload models between stages.

### 5.3 UV, alpha and pattern preservation

Three output modes within **the same pipeline**, not three competing base models:

1. **Repeating material**: substantial reconstruction and new surface detail; enforce periodic seamless left/right and top/bottom edges; assess a 3×3 repeated preview. Use periodic boundary-conditioning (wrap/pad/circular-offset techniques), seam-aware repair and source-tile alignment as appropriate. Do not merely blur a bad seam until it vanishes.
2. **Nonrepeating mapped surface**: preserve large shapes and alignment to the original UVs. Do not shift door frames, window edges, garment seams, painted symbols or structural outlines just to make an attractive image.
3. **Protected/specialist**: masks, 513 `shadow*` tiles, UI icons, unreadable/unknown images, critical text/alpha atlases are not converted to surface albedo by the first cohort. Record a reason and direct them to later specialised processing, not a generic upscale or hallucination.

Keep source orientation, colour channels, and any real alpha support. For opaque JPEG, do not fabricate alpha. For a later alpha-bearing asset, operate on RGB without damaging the alpha mask and reattach exactly the intended alpha, unless the asset-specific workflow explicitly changes it. Strongly preserve mask boundaries and texture registration for cut-outs.

### 5.4 Family consistency

Ground tile sets and transition tiles may be adjacent in-world. A generated transition should be conditioned on compatible base textures and must maintain its edge and blend semantics. If transition semantics cannot be reconstructed from the catalogue, mark for the **family-aware specialist workflow** rather than introducing visibly broken seams. Reuse measured colour statistics and shared prompts; don't allow every brick or sand variant to adopt an unrelated art style.

### 5.5 Outputs

Per generated asset, keep `source`, `raw_qwen`, `albedo_final`, `normal`, `depth_raw`, `height`, `orm`, `diagnostics`, `prompt`, `seed`, `model hash`, `runtime`, `status`, `rejection reason`. Retain intermediates outside Git so debugging doesn't require rerunning the model.

## 6. PBR construction

**Input:** accepted generated albedo, **not the unenhanced original**. PBRFusion 4 outputs normal and depth/filtered-depth. Derive:

- **`_n.png`:** OpenGL tangent-space normal RGB, +Y; resize to target resolution with normal-vector renormalisation. Respect ao-vk's lack of supplied tangents and its derivative-based normal bending. Avoid making all surfaces look like deeply embossed plastic.
- **`_h.png`:** greyscale relative relief from normalised/filtered predicted depth, with class-specific range/contrast. It is *apparent relief*, not measured metric displacement. Make parallax scaling configurable; check for inverted height semantics.
- **`_orm.png`:** 8-bit RGB with red ambient occlusion, green perceptual roughness, blue metallic. Initialise via explicit material-class policies (e.g. sand/stone nonmetal with high roughness, painted metal with mostly dielectric paint and exposed-metal local areas, bare metal high metallic, fabric high roughness). Refine with meaningful spatial analysis where supported. Do not derive metalness simply from brightness. Compute AO from relief carefully and weakly (avoid double-darkening ambient lighting). Unknown materials default nonmetal/rough and are flagged for future classification.
- **`_d.png`:** colour albedo. Correct gamma/sRGB for colour while treating normals/ORM/height as data. Preserve source look at macro scale, avoid baked shadows/highlights where possible.
- **`_e.png`:** only for explicitly labelled emissive displays/lights. Do not infer glowing emissive maps from white stone or bright sand.

Normal/height/roughness and albedo must describe **the same features**: an impressive-looking normal map that doesn't match the generated cracks is a defect. Generate every PBR channel at appropriate alignment and resolution; maintain periodic boundaries for tilable assets across all maps. Images must pass ao-vk's documented PNG conventions. Include a simple offline shaded-sphere/plane preview with adjustable light direction to reveal inverted normals, plastic-looking roughness and fake relief.

## 7. Automated quality gates (production hygiene, not a bake-off)

Hard-fail / quarantine only when needed to prevent broken assets from reaching the game:

- Decoder cannot load input/output, wrong dimensions/aspect ratio, missing output, invalid PNG, empty/black/NaN image, inconsistent alpha, or corrupt channel count.
- Severe **introduced** periodic seam versus original's measured seam quality (for marked tileable materials). Compare boundary derivatives to adjacent interior edge gradients, not one arbitrary raw-difference number across all material classes. Export 3×3 preview for diagnostic.
- Original UV-critical large shapes/text radically moved, or source has a high-risk atlas/mask disposition (route to specialist instead of generative production).
- Normal map invalid range/direction or gross mismatch; ORM outside [0,1], height missing, obvious inverted/shadow baking.
- Installed filename not traceable to an original RDB `(type,id)`.

**Do not reject an image merely because its pixel difference from the original is large.** The objective is bold re-authoring. Log colour shift, LPIPS/embedding similarity if useful, edge metric, brightness, entropy and generated-detail statistics as *diagnostics*, not a blanket preference for conservative output. Flag obviously unrecognisable outputs for review.

On failure: one automatic retry with targeted parameter or seam correction; afterwards quarantine with a reason. Do not replace the failed output with a simple upscale without expressly recording a fallback and user-visible result. Emit every unsuccessful ID in the final report.

## 8. Orchestration, caching and provenance

Use a **persistent job database** separate from `assets.csv`, with per-stage statuses:

`pending -> extracted -> generated -> pbr -> qa_passed -> packed`, with branches `retry`, `rejected`, `blocked` and `failed`.

For each stage, compute a content-addressed cache key from **source SHA, model revision/weights hash, config revision, family prompt version, seed and stage implementation version**. Atomic file writes: write to temporary paths, validate, then rename. Jobs resume after Ctrl+C, machine restart or ComfyUI crash. Keep a heartbeat and recover interrupted jobs. Retry deterministic network/model download failures; don't loop indefinitely on CUDA OOM. No unbounded background workers or cross-GPU batch concurrency by default.

Maintain two independent logs: per-asset event JSONL and high-level readable run report. Include maximum VRAM (CUDA and/or `nvidia-smi`), GPU model/driver, wall time by stage, power consumption only if measured, errors, file sizes and throughput. Stage timing must not conflate model load with inference.

Avoid keeping multiple 2K RGBA images or all extracted textures resident in RAM. Use bounded CPU queues, GPU concurrency one, stream data from disk and unload unused models when switching stages.

- Per-asset original / generated albedo / normal / height / roughness / 3x3 tile preview / a relit material preview, with click-to-full-resolution.
- Side-by-side before/after and short per-asset metadata; no need to inspect all outputs manually.
- Family overview: one representative hero image plus variants and their statuses.
- An `in-game-evidence/` section for screenshots captured from live PRK with before/after at same position, TOD and graphics settings where possible.

This gallery is an operational tool for spotting failures and seeing genuine improvements, not a criterion that blocks a production run.

## 11. Expansion after v0.1

**The system is designed for the entire 13,410 primary gameplay-texture space**, not merely the easy 1,076. Avoid building an architecture that makes later expansion painful.

1. **v0.1:** run and install the complete 1,076 initial material cohort; assess actual in-game improvement in Shadowlands and Rubi-Ka environments. Fix material-family problems and regenerate affected assets.
2. **v0.2:** use VLM/image embeddings and the existing catalogue to classify the **3,271 unlabeled assets**; automatically route actual surface textures into the same **Qwen + PBRFusion** pipeline. Rebuild families. Exclude masks/UX/effects by evidence, not lexical absence. Run a real additional production batch.
3. **v0.3:** specialist classes using the **same Qwen generator** but with explicit UV-layout/alpha/identity constraints: clothing (3,115), faces (336), decals/signage (478 candidates), cut-outs (1,881 risk tags), dungeon transition tiles and other mixed atlases. Texture-sensitive outputs may need bounded, masked edits and class-specific QA. Icons (7,449) remain a separate UI-restoration product decision; do not automatically let Qwen redesign inventory symbols.
4. **Later:** character geometry/meshes (9,925 static and 770 character mesh records from prior census), richer vegetation and terrain. **Out of scope for this texture repository's v0.1**; track integration ideas without blocking texture delivery.

`13,410` is a *record count*, not an assurance every image should be aggressively edited. Every ID should eventually have an explicit disposition and rationale. The mission is maximum visible improvement, not an artificially inflated processed count.

## 12. Testing and acceptance

### 12.1 Unit and integration tests

Test using generated synthetic fixtures (not copied game art):

- SQLite/RDB extraction with read-only checks; catalogue CSV schema mapping; RDB ID joining; arbitrary table/type counts.
- Duplicate treatment and stable asset IDs; material-family planning; exclusive dispositions and overlapping tags.
- Image decoding, format/orientation/alpha, aspect ratio and map channel packing.
- Tileable-image seam metrics; intentional failure and valid repair; non-tileable UV preservation detection.
- ORM red/green/blue order; OpenGL normal Y convention; normal-vector renormalisation; height numeric ranges.
- Mock local ComfyUI API for orchestration tests, not to claim actual generated art. Test crash/restart and idempotence.
- Correct pack filenames, precedence, dry-run install/disable, backups and absolutely no edits to `rdb.db`.
- Run manifests complete with correct counts/statuses and hashes; no silent partial successes.

### 12.2 GPU/inference integration

Actual Qwen Turbo image-conditioned editing output on RTX 5080 under Linux using the selected local inference stack; true 8-step checkpoint semantics; measured memory, throughput and output provenance. Actual PBRFusion normal/depth on this output. A real successful material job is an intermediate technical milestone. **It is not the final deliverable.**

### 12.3 v0.1 release gates

- Working code, real model integration, and production CLI documented and committed in the new repository.
- First cohort accurately reconciled against original 1,076 IDs; every ID receives a terminal status, and all successful images are present in the pack.
- Qwen-generated albedo and aligned normal, height, ORM for each packed surface; no misleading substitutes or generated fake records.
- Pack validates and is installable/disablable with an intact original client.
- Gallery and report reflect actual run outputs, including failures rather than hiding them.
- **A visible material change in PRK** using the installed pack is demonstrated by at least one repeatable in-game comparison. If a user-run game session is necessary, generate exact minimal capture instructions and mark that single gate pending user validation. Do not claim it happened automatically.
- Exact performance and model-memory numbers from the user's machine, not illustrative estimates.

### 12.4 What constitutes failure and how to pivot

- **Qwen cannot run at usable quality or throughput on 16 GB even with quantisation/offload:** record logs, peak VRAM and attempted optimisations. Only then propose a lighter generator or a hybrid resolution workflow.
- **Outputs look attractive in isolation but destroy tiling/UV registration:** improve conditioning, family processing, seam constraints and preserve macro structure. Don't immediately abandon generative re-authoring.
- **PBR maps don't match generated surfaces:** fix normal/height alignment, roughness and material-class policies. Don't substitute blanket flat maps and call the pack complete.
- **In-game effect barely noticeable:** prioritise textures that dominate scene area, increase meaningful high-frequency detail/relief and adjust material/render settings. Capture comparison evidence. This is the key aesthetic test given the preceding DLSS 5 disappointment.
- **Game performance or loading regresses:** measure per-texture decoded memory, loader behaviour, mip quality and pack size; choose class/LOD-specific resolutions and, if needed, add a separate optimised image storage/streaming path rather than blindly reducing every source to 512px.

## 13. Non-functional requirements

- **Local/offline inference once weights are cached.** Never silently use hosted APIs or upload PRK textures to third parties.
- **No data loss:** PRK database is read-only; original ao-vk code and working DLL untouched; manifests and order backups preserved.
- **No copyrighted game art in Git:** ignore database, decoded images, generated packs, model weights and test screenshots of PRK. Use synthetic assets for checked-in tests and examples.
- **Resumable, inspectable, deterministic where practical**, per-ID audit trails and per-stage logs.
- **Robust under OOM:** unload and retry with explicitly recorded memory settings; no infinite jobs.
- **Fits Linux RTX 5080 16GB as configured**, without assuming full BF16 residency of the whole Qwen stack; document system RAM and disk requirements measured during setup.
- **Developer ergonomics:** one documented bootstrap, one run command, one status command, one gallery, one build/install command. Do not make the user edit long ComfyUI workflows manually.
- **Honest reporting:** distinguish asset count, successful model generations, accepted pack entries, in-game visual improvements and unresolved items.
